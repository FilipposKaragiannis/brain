01The flows

You file an item. Its kind and size pick a line. The run follows the line and stops at every diamond.

02Playbooks

Real sessions, step by step. Type what the dark box says, or switch to Plain words and say it. A $ box goes in a terminal or a scheduler. The diamond is where you answer.

You have an idea that needs several PRs.

  2. 2
    ›/flow:next gh#310$next gh#310Grill me on gh#310

Work the backlog unattended

The tasks are filed, grilled and sized. Agents work them while you are away.

  1. design
  2. plan
  3. plan-approval
  4. implement
  5. test
  6. review
  7. verify
  8. pr
  9. merge
  1. 1
    In .flow/config.yaml: auto_gates.plan-approval: S,M and notify.idle: true

    Small and medium plans pass on their own. Merge and every other gate still wait for you.

  2. 2
    ›/flow:board$boardWhat is ready?

    Check what is ready. A run takes ready tasks in list order; blocked ones wait.

  3. 3
    $.flow/run-unattended.sh claude --max-steps 15.flow/run-unattended.sh codex --max-steps 15Start a one-off unattended run on the queue

    One run by hand first. It takes the first ready task, claims a worktree and runs every step as a fresh process with that agent's model and effort.

    explorerarchitectplannerimplementertest-writerverifierpr-creator
    mergeReview the PR. Merge it on GitHub.
  4. 4
    $<repo>/.flow/jobs/next.sh claude --max-steps 15 --workers 2<repo>/.flow/jobs/next.sh codex --max-steps 15 --workers 2Run a repeating unattended flow every 30 minutes, two at a time

    Schedule it every 30 minutes: a Claude Desktop scheduled task, or launchd. Each worker takes its own ready task and worktree, works it to the next gate and logs to .flow/log/next-<n>.log. The pool caps the workers.

  5. 5
    ›/flow:gate gh#312 "merged"$gate gh#312 "merged"gh#312 is merged

    Your merge unblocks the tasks behind it. The next scheduled run starts one.

  6. 6
    The queue runs dry.

    notify.idle sends one notice, on the desktop and in Slack, then stays quiet until a run does work again.

From a playtest note to an issue

You jot notes while you play. An agent files each one overnight.

  1. implement
  2. test
  3. review
  4. verify
  5. pr
  6. merge
  1. 1
    In .flow/config.yaml: intake.notes: docs/notes.md, a file in the repo; jobs.permission_mode: auto

    One bullet per note, sub-lines under it. Headings are hints at the kind and the area.

  2. 2
    $.flow/jobs/intake.sh claude --batch 3.flow/jobs/intake.sh codex --batch 3File my next three notes

    One run by hand first. Each note gets its own fresh session: it checks the open items and the code, then files a typed, sized item with a suggested priority, or names the item it duplicates.

    → gh#341 to gh#343; the three notes leave the file, which is committed and pushed
  3. 3
    $<repo>/.flow/jobs/intake.sh claude<repo>/.flow/jobs/intake.sh codex<repo>/.flow/jobs/intake.sh claude

    Schedule it nightly: a Claude Desktop scheduled task, or launchd. The ledger in .flow/log stops a note being filed twice.

  4. 4
    Set the Priority field on the new items.

    The agent only suggests one. An item without a priority is never ready, so nothing starts before you look.

  5. 5
    On the issue, comment: /answer as recommended, but 2 is a lunge

    A note the agent could not turn into testable lines waits at the ambiguity gate: numbered questions, each with a recommended answer. The next scheduled run reads your /answer, clears the gate and hands your words to the next step.

    ambiguityAnswer the questions in a sentence each.
  6. 6
    ›/flow:next$nextStart the next ready task

    The new items join the queue in priority order, by hand or on the unattended schedule.
