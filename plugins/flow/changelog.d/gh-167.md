bump: minor

- An item's work starts from its base and its PR merges into it, resolved once when it is first
  claimed (gh#167). In order: the branch of the parent's claim; the `epic/<n>` branch of the
  nearest ancestor (up to five levels) that has one on the remote; a `base: <branch>` line in the
  item's body; the config `base`. A `base:` line naming a branch that is not on the remote, or a
  name that is not a valid branch name, passes the item over with exit 4 and says so in
  `last_event`, rather than cut the work from the config base. The claim records the base in
  `.flow/claim.json` and in the new state key `base`, and `events.log` gets a `claim` line naming
  the base and why.
- Every reader takes the recorded base: the brief's `(base ...)` and `next.sh --json` `base`, the
  pre-verify sync, `verify.sh` (its `changed_files` diff), the health job's merge of a branch that
  fell behind, the note when a hold is released, and the pr-creator, which opens the PR against
  it. When the item's `state.base` is set, the pr-creator reads the base from `.flow/claim.json`
  and stops when the two differ; a claim made before this change has no `state.base` and keeps
  the old parent rule. The pr-creator refuses a base that starts with `-`, has a character
  outside `A-Za-z0-9._/-` or fails `git check-ref-format --branch`; a claim takes no such base
  either (`steward.sh claim --base` exits 2), and the board and `init` skip a claim recording
  one. The planner says each
  split child is claimed from the base its claim resolves.
- The board names a base other than the config base beside the item's worktree
  (`wt-1, base epic/525`), and `board.sh --json` gives `base` and `base_missing` on each pool
  entry. A claim whose base is not on the remote (deleted after the claim) shows in Health,
  `<item>: base <b> is not on the remote`, and `init` notes it; neither fetches.
- A verify run can outlast any one shell call the host allows (a 10 minute cap killed it in the
  middle of a slow gate, with no report). `verify.sh <item> --start` starts the run detached in
  its own session (output in `<reports>/verify.out`, the run in `<reports>/verify.run`) and
  returns at once; it removes the earlier `verify.json` and `verify.md` first, and a run already
  going is not started again. `verify.sh <item> --wait [seconds]` (default 540) exits 0 on pass,
  1 on fail and 3 while the run goes on, with the time so far and the check it is on; a run that
  died with no report gets a fail report. The new key `verify.limit` (default `2h`) stops a run
  that takes longer, with its whole process group, and the fail report names the check and the
  limit. The verifier starts the run and waits in short calls; plain `verify.sh <item>` runs in
  the foreground as before. The health job and the comments job count a detached verify run as
  the item's live run, and `steward.sh release` and `stop` end it.
