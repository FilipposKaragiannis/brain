bump: minor

- An item's work starts from its base and its PR merges into it, resolved once when it is first
  claimed (gh#167). In order: the branch of the parent's claim; the `epic/<n>` branch of the
  nearest ancestor (up to five levels) that has one on the remote; a `base: <branch>` line in the
  item's body; the config `base`. A `base:` line naming a branch that is not on the remote passes
  the item over with exit 4 and says so in `last_event`, rather than cut the work from the config
  base. The claim records the base in `.flow/claim.json` and in the new state key `base`, and
  `events.log` gets a `claim` line naming the base and why.
- Every reader takes the recorded base: the brief's `(base ...)` and `next.sh --json` `base`, the
  pre-verify sync, `verify.sh` (its `changed_files` diff), the health job's merge of a branch that
  fell behind, the note when a hold is released, and the pr-creator, which opens the PR against
  it. The planner says each split child is claimed from the base its claim resolves.
- The board names a base other than the config base beside the item's worktree
  (`wt-1, base epic/525`), and `board.sh --json` gives `base` and `base_missing` on each pool
  entry. A claim whose base is not on the remote (deleted after the claim) shows in Health,
  `<item>: base <b> is not on the remote`, and `init` notes it; neither fetches.
